# Internationalisation

The app reaches German, English, and French along two independent paths that share one
active-locale signal. **Vocabulary-derived labels** (field names, controlled-vocab terms)
come from the `vocab/*.ttl` documents at build time. **App chrome** (everything else —
nav, headings, buttons, dialog labels, empty states, toasts) comes from a small in-app
message catalog. This note covers the chrome path.

## Shape

The catalog is rolled in-house — there is no i18n library dependency. It is a thin layer
over the platform `Intl` API, living almost entirely in `src/lib/messages.ts`:

- **`MESSAGES`** — one object literal keyed by a stable id, each entry carrying a string
  per language (`{ de, en, fr }`), or, for counts, one string per `Intl.PluralRules`
  category (`{ one, other, … }`). Bundled in the source — no resource files, no runtime
  fetch, no async load.
- **`translate(lang, id, params)`** — the core: looks the entry up, selects the plural
  form with `Intl.PluralRules` when `count` is present, then fills `{name}`-style named
  placeholders (never positional). `MessageId` is the union of the catalog's keys, so a
  typo is a type error.
- **`msg(id, params)`** — imperative; resolves in the *current* active locale
  (`getLanguage()` at call time). For one-shot strings fired outside render — toasts in
  handlers, and labels in dialogs/detail pages that aren't open across a locale switch.
- **`useT()`** (`src/context/I18nProvider.tsx`) — the reactive counterpart for render
  strings on long-lived surfaces (finders, the app shell); it re-renders in place when
  the locale changes.

The active locale is a separate pure store (`src/lib/language.ts`,
`getLanguage`/`setLanguage`): seeded from `navigator.languages` (region-stripped),
persisted to `localStorage`, and read in render via the `useLanguage()` hook
(`src/hooks/language.ts`) — the same store-below / hook-above split as the other
client stores. The one signal drives both the catalog and the vocab-derived labels;
the language switcher is a fixed entry in the account menu.

Two invariants are test-enforced. A unit test asserts every catalog id carries all three
languages, so a half-translated entry can't ship. The e2e specs assert against the
catalog rather than literals — `en(id)` (a helper reusing `translate`) — and the
Playwright UI locale is pinned to English, so a copy edit to a string can't silently
desync the specs that locate it.

## Why no library

The chrome path only needs a string map: the heavier half of i18n (the field/term
vocabulary) is already handled at build time from the ontologies, and `Intl.PluralRules`
/ `Intl.NumberFormat` ship with the runtime, so plural selection and number formatting
are free. A bundled literal needs no loader, no extraction step, and no async — which
also keeps it Deno-friendly (the same runtime constraint that has steered other choices
here away from libraries that assume Node). react-i18next or FormatJS would add a
dependency and a message-pipeline to manage a few hundred keys in one file.

The cost, should it grow: the placeholder grammar is `{name}` plus plural categories, not
full ICU MessageFormat (no gender/select, no nesting); translations live in code, not in
per-locale files a non-developer could edit; and there is no `.po`/translator-tooling
export. All of that is deferrable until there is an actual translator workflow — the
stable ids make a later extraction mechanical.
