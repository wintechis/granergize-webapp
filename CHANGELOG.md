# Changelog

All notable changes to the Granergize WebApp project will be documented in this file.

## [2026-06-06]
- Fix the recipient's **"Views shared with you" row showing an opaque snapshot id** (`view-<timestamp>-<random>`) instead of the view's name. The recipient holds Read on the computed *snapshot* (which carries `gran:viewName`) but not the definition, and the row only fetched the snapshot lazily on "Show values" — so before expanding it fell back to the bare id, useless in a "shared with you" list. `ReceivedViewRow` (`SharePage.tsx`) now loads the snapshot **once on mount** so the name shows up front; expanding reuses the already-loaded snapshot (no refetch), and a load failure still falls back to the id rather than erroring. Confirmed green by the Tier-3 `share-view` e2e (A shares a view → B sees it *by name* + values render → A deletes it → B no longer sees it)
- Fix the Tier-3 `share-view` spec hanging at "B not yet listed as a room member": the member-listing step polled the share dialog with `add.isVisible({ timeout: 5_000 })`, but **`locator.isVisible()` does not wait** — its `timeout` arg is a no-op, so the immediate check always raced the dialog's async member load, closed the dialog, and looped forever. Instrumenting `loadMembers` proved the data layer was never at fault: `getActiveRoom()` returns A's room and `getMembers` folds **both** Alice and Bob on every call (the earlier "null singleton" / "dropped join" hypotheses were both wrong). The spec now uses a **waiting assertion** (`expect(add).toBeVisible({ timeout })`) inside the re-open loop (the loop is kept for genuine remote-Pod propagation lag on Tier 4)
- Fix a building's **Energy view showing "No energy data available" right after the demo seed** (and after any change to the building set): `useEnergy`'s React Query key was the constant `["energy", webId]` with no dependency on the building list, so energy was computed once for the then-current (often empty) set and never refetched when buildings changed — the annual `<year>-P1Y.ttl` datasets were written but never read back into the view (confirmed: written, never GET). The energy query is now **keyed on the sorted building ids** (`queries.ts`), so it auto-refetches whenever the set changes; the now-redundant, race-prone explicit energy invalidation in the demo seed (`index.tsx` `seedDemos`) is removed. Caught by the Tier-3 `view-data` e2e (the series demo building masked it — its heading renders from the building TTL's dataset declarations, while the annual figure comes from the energy query)
- Tests (Tier 3 reliability): make the local-CSS browser tier dependable enough to run green. The boot **token-verification warmup now retries the whole client-credentials acquisition** (not just the final GET) — the residual "no applicable key found in JWKS" 401s were the warmup's own first calls losing the boot race and being silently skipped, so warming never ran; a full suite now logs **zero** auth errors across ~20 per-spec CSS reboots. The per-spec **`/reset` now waits for the CSS port to actually free and retries the boot** instead of a blind 500 ms (fixes an intermittent exit-code-1 on restart). Tier 3 serves the app on its **own port** (`LOCAL_APP_PORT` = 4183; `E2E_PORT` overrides) so it can run **concurrently with a Tier-4 real-Pod run** without racing to bind 4173. New `LOCAL_CSS_LOG=<path>` tees CSS's full debug log to a file (off by default; `-l debug`) to attribute substrate flakiness. Spec robustness: `energy-entry`/`organisation` teardown returns to the app shell first (the standalone `/energy/:id` route has no tabs, so a cleanup tab-click hung the hook) and bounds its clicks (Playwright's default action timeout is 0 → an un-actionable click could consume a whole hook budget *uncatchably*, defeating the best-effort try/catch); `view-data` targets the annual `Nordostpark` demo building deterministically; `excel-export`'s final id-set assertion polls for the post-delete refetch instead of reading once; `organisation` verifies provenance via Create-View's role list (which only offers roles present in the data) rather than selecting a "User" option it never offers
- Tests: reorganize into **four tiers** that climb fake→real one axis at a time — unit (`deno task test`) → CI/headless against a local CSS (`deno task it`) → **browser e2e against a local CSS** (`deno task e2e:local`, NEW) → e2e against real Pods (`deno task e2e:remote`; `e2e:remote:spec` runs one spec by path). The new Tier 3 reuses the real-Pod UI specs via a Playwright `local` project (`E2E_LOCAL=1`) driven against a throwaway local Community Solid Server with two seeded pods — credential-free and CI-able, filling the browser×local-CSS gap so UI/render bugs are caught hermetically before the credentialed real-Pod run. Both tiers use **two roles, A = Alice and B = Bob** (solo specs → Alice; sharing specs → Alice + Bob); for Tier 4 you configure each role's Pod/WebID per run by `source`-ing a `test/.env.e2e.*.local` file — provider selection IS which file you source, so the same specs cover solidcommunity vs solidweb vs redpencil without any launcher script. `interoperates()` lets two distinct-WebID pods on one provider form the sharing pair. See `test/README.md`
- Fix the login screen mangling a fully-qualified identity-provider URL: the "another identity provider" field blindly prepended `https://`, so a pasted `https://…` URL (or an `http://localhost` dev/test issuer) became `https://http://…` and failed with "Please provide a correct URI". A value that already carries a scheme is now taken as-is; only a bare domain gets `https://` (extracted as `normalizeIssuer`, + unit tests)
- Fix an infinite render loop ("Maximum update depth exceeded") on the Connect tab for a brand-new user with no active data room: `useRoomState` returned a fresh `[]` for `myRoles`/`members`/`known` on every render when there was no current room, and `ConnectPage` used `myRoles` as a `useEffect` dependency, so the role-sync effect re-ran forever. The empty fallbacks now reuse one frozen array (`queries.ts`), so first-login (and any no-room state) is stable (+ a `useRoomState` regression test)
- Pod writes survive a transient connection abort: `withRetry` now also retries a browser/connection-level abort the caller did NOT request (our writes are idempotent — PUT-whole-file / append-via-POST — so replaying is safe), while still NOT retrying a request the user cancelled (its own `AbortSignal` is aborted). Also lengthen the Cloudflare backoff to 2 s → 4 s → 8 s across the three retries (+ tests)
- Storage-root discovery follows the Solid convention more fully: `resolveStorageRoot` reads `pim:storage` from the WebID profile, else walks up to the `pim:Storage`-typed container (so a Pod that types its root but omits the triple still resolves); adds `resolveStorageRootForWebId` for an arbitrary recipient's root. And the app's notification inbox is now **app-scoped** at `<storageRoot>/granergize/inbox/` (not the agent-global `/inbox/`), discovered via an `ldp:inbox` pointer on the `granergize/` root with a convention fallback, and **self-provisioned at login** (`ensureOwnInbox`: container + append-only `.acl` + pointer) so the app works on a bare Pod. Production behaviour change — older shares sat on `/inbox/`
- Tests (Tier 3 internals): the local CSS is booted by `test/e2e-local/css.ts` and **restarted per spec file** (a control server that `login()` triggers once per file) so specs never share mutable pod state; its stdout/stderr are drained (an undrained pipe buffer would deadlock CSS under load → a whole-run cascade) and it fails fast if CSS dies; and token verification is **warmed on boot** to mitigate an intermittent CSS "no applicable key found in JWKS" 401 just after boot — a local-CSS OIDC-substrate timing race (the data layer is fine: when the token verifies, CSS returns 201 and the write lands), never seen on real Pods. Documented in `test/README.md`
- Tier 4 writes to a **separate app collection** so the browser e2e never touch real data: every on-Pod path is built from one source of truth — `APP_DIR` / `appRoot(webId)` in `solidUtils.ts` (from `VITE_POD_APP_DIR`, default `granergize`) — and every `deno task e2e:*` run sets it to `granergize-e2e`. Routed the ~10 previously-inlined `<storageRoot>granergize/…` builders through it (rooms, shared-in/out, prefs/hidden-buildings, bookmarks, views, buildings, inbox, the wipe); the structural-folder provisioning notice (`podWrite.ts`) keys off `APP_DIR` too. Adds **`deno task e2e:remote:reset`** — a Playwright `reset` project (`test/e2e/maintenance/reset.spec.ts`) that wipes the e2e collection for both roles (Alice + Bob) via the app's own "Remove all app data" path, **gated on `E2E_RESET`** so a normal run can never trigger the wipe. Corrects the stale `hiddenBuildings.ttl` reference in CLAUDE.md (it was folded into `prefs.ttl`). + unit tests for `appRoot`/`APP_DIR`
- Tier 4: the spec runner now **aborts the whole run the instant a Pod host behind Cloudflare answers Error 1015** (rate limited), instead of grinding every remaining spec through its retries/backoff and a multi-minute timeout against a tripped limiter. The 1015 page is an edge HTTP 429 with no CORS header, so the app's own JS only ever sees `TypeError: Failed to fetch` (see `retryFetch.ts`); Playwright sees the raw 429 at the network layer, so a per-page response watcher (`cloudflareGuard.ts`, attached in `login()`) writes a sentinel and a main-process reporter (`cf1015Reporter.ts`) `process.exit`s on it. The pure detector (`cloudflare1015.ts`) is unit-tested — it distinguishes a real edge-1015 from a normal CSS 429-served-with-CORS (which `retryFetch` rightly retries)

## [2026-06-05]
- Demo buildings are now offered, not silently written: on a fresh Pod (no `buildings/` container) the app no longer auto-seeds two example buildings — instead a dismissible info **banner** ("No buildings yet — add a couple of example buildings to explore?") offers **Add examples** / **No thanks**, with the decline remembered in `prefs.ttl` (`gran:demoSeedDeclined`) so it doesn't nag. An avatar-menu **"Create demo buildings"** adds them on demand. And **"Remove all app data" no longer forces a logout** — it stays in the now-empty app, resets the query caches, and re-offers the demos (the forced logout only existed because startup used to re-seed the just-deleted data). The banner is non-blocking, so it doesn't get in the way of adding your own buildings
- E2E: collapse the `sharing` and `view-sharing` specs from 4-/6-part multi-process splits into a single test each, driving two browser contexts (A and B) in-process. The split only ever existed to stay under solidcommunity.net's Cloudflare burst limit; on the reliable Pods it's unnecessary, so the gitignored state-file handoff and the `-g "part N"` choreography are gone. A 2 s cooldown sits at each write→read handoff. Both are now fully self-cleaning in `finally` (A deletes its building/view + room, and B drops its bookmark of A's room via a new `removeAllBookmarkedRooms` helper). Also made `building-delete` and `energy-entry` self-cleaning (add-then-delete their own building rather than consuming/mutating a seeded one), and `provenance` restores the prior profile role in `afterAll`
- Building coordinates are now a `geo:Point` blank node carrying their geocoding precision, instead of flat `geo:lat`/`geo:long` on the building: `<#b> geo:location [ a geo:Point ; geo:lat … ; geo:long … ; gran:geocodePrecision … ]`. `gran:geocodePrecision` is IRI-valued (`gran:Address` / `gran:Postcode` / `gran:City`) and records how precise the lookup was, so an approximately-placed building (only its city resolved) is distinguishable from a rooftop hit. Both write paths go through one helper — `serializeBuildingToTurtle` (new buildings) and `updateBuilding` (edits, which migrates a legacy flat-coordinate building to the point on save); the parser prefers the point but still reads legacy flat coordinates as a fallback, so existing Pods and fixtures aren't orphaned. New `geo`/precision constants in `vocabularies.ts`; adds unit tests (point + precision written, not flat, round-trips; legacy flat still parses)
- Importing a building template now geocodes it on import (PROBLEMS.md #6): the investor/BSP templates carry an address but no coordinates, yet lat/long are required, so a bulk import previously couldn't be submitted at all. `handleFileUpload` now resolves each parsed building's coordinates via the shared `geocodeFields`, which tries progressively coarser queries (full street → postcode + city → city) so a too-precise house number a geocoder can't place still yields an approximate pin (recording the matched precision, see above), throttled to Nominatim's ≤1 req/s. `geocodeFields` is exported from `buildingSerializer` and now backs the demo seed and BOTH the Add and Edit dialogs' "look up coordinates" buttons (was the same Nominatim call copied in three places). Also fixes a real accessibility defect surfaced by the e2e: the Add dialog's `Template` `<Select>` (and the `enumSelect` helper) had no `labelId`, so it had no accessible name — `getByLabel("Template")` and screen readers couldn't find it
- E2E: make `excel-upload` reliable and self-cleaning — it stubs Nominatim with deterministic coordinates (an e2e must not depend on a rate-limited third-party geocoder), polls the Manage list for the post-import refetch instead of reading it once, accepts the `Delete building` `window.confirm`, waits for each building's row to vanish rather than the lingering "Building deleted" toast (which let the cleanup loop race and leak buildings), fills location fields for the address-less Lastgang file, and no longer depends on demo seeding. `data-room-switch-debug` gains an `afterAll` cleanup net (the shared `deleteAllOwnedRooms`) so a mid-switch timeout — its common failure — can't leak the rooms it hosts
- Building provenance is now set once in your WebID profile, not chosen per add (PROBLEMS.md #1 / Handbuch HW5 — **Done**): a "data-producer role" stored as W3C `org:role` on an `org:Membership` (`organizationManager.ts` `get`/`saveProducingRole`), set in the Organisation dialog and applied automatically as `prov:hadRole` on every building you add (`AddBuildingDialog` reads it via `getProducingRole`). The Add dialog's Template selector is now spreadsheet-shape only; unset role → no attribution is written, with an inline nudge to set one. Finishes separating `UserRole`'s three jobs (template / provenance / data-room role). Adds a round-trip unit test and a `provenance` e2e (set role = Investor, add a building with the *User* template → it filters under Investor, not User, in Create View)
- Aggregated-view revocation now notifies the recipient (PROBLEMS.md #21, the view half — building revocation already did): `revokeViewAccess` posts an `interop:AccessRevocation` to the recipient's inbox (best-effort, via the now resource-neutral `notifyAccessRevoked`), so on their next inbox drain the view folds out of `shared-in/` and disappears from "Views shared with you" — instead of lingering with values that no longer load. Deleting a shared view is covered too: `useDeleteView` revokes (and notifies) every recipient via `revokeAllViewRecipients` before deleting the snapshot, so it doesn't leave a stale row either.
- Aggregated-view sharing now has a recipient side (PROBLEMS.md #17): a view shared with you appears under a new "Views shared with you" section on the Share tab and opens to its computed values (a table + the same SVG bar chart the owner sees). Previously the `kind:View` grant reached your `shared-in/` log but nothing surfaced it — `getSharedViews` was sender-only, `SharePage` listed only buildings, and `/#/view/:id` resolved against your own Pod. Adds `getReceivedViews` (folds `shared-in/` for `View`, mirroring `getSharedWithMe`), `useReceivedViews`, a login-time invalidation, and renders the snapshot via the existing `loadComputedSnapshot`. Adds a two-pod `view-sharing` e2e covering the full lifecycle (A hosts a room → B joins → A creates+shares a view → B sees it + values render → A deletes the view, revoking B → B no longer sees it), plus unit tests for the fold
- E2E: add `excel-export` (PROBLEMS.md #8) — asserts the browser download fires with the expected filenames (`buildings-mine.xlsx` / `building-<id>.xlsx`) and that an exported workbook re-imports to the same buildings (full round-trip through Add Building's file picker, then deletes the copies). Destructive; expects a reseeded Pod
- E2E: a shared `deleteAllOwnedRooms` helper (`e2e/helpers/rooms.ts`) lets a spec delete the data rooms it hosts in a final cleanup part, so the `sharing` and `view-sharing` runs no longer leak rooms on the Pod across runs
- Decouple "Add Building" from data-room roles (PROBLEMS.md #1, one more step): adding a building to your own Pod no longer requires holding a self-assigned role in a data room. The Add dialog's selector is now a plain import **template** chooser (always populated; the old "You have no role assigned in the data room…" dead-end and the disabled "Add Building" button are gone), finishing the half-done Role→Template rename in the UI (`AddBuildingDialog.tsx`). The `excel-upload` e2e drops its room-role skip and selects the template directly
- Keep the map's building detail pane view-only: the two write actions that had leaked into it — "Upload/Replace energy certificate" and "Add / edit energy year" — move to the Manage tab as per-building row actions (next to Edit / Share / Download / Delete), where outgoing-data actions belong. The standalone `/building/:id` page (unreferenced in the app) drops them too, and `Building` no longer needs a `session` prop

- E2E: `energy-entry` now opens the per-year energy dialog from the Manage row action (was the standalone building page)
- E2E: add `building-delete` (PROBLEMS.md #3) — adds a throwaway building, asserts it appears on Manage, then deletes it via the "Delete building" row action and asserts the row is gone and the count is back to the start. Self-cleaning (adds + deletes its own building)

Record the spec/test coverage for the fixed items
